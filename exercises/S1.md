# S1 — Concurrent-safe idempotency

**Planned for V0.3 · Senior · 25–30 minutes**

A transaction commits but its response is lost. Retrying with `Idempotency-Key` must return the original result. The same key with a different payload returns 409. Scope keys by client and operation. Concurrent duplicates must create exactly one financial record across multiple application instances. Failed operations cannot leave successful idempotency results.

Discuss and test database uniqueness, request fingerprints, atomic persistence, retries, concurrency, and recovery on real PostgreSQL. The V0.1 starter supplies no IdempotencyRecord, implementation, or exercise task. A single-instance map or lock is insufficient evidence of the required guarantee.
